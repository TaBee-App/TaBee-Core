\section*{\centering\thetitle}
\centerline{\fontsize{16pt}{21.6pt}\sffamily\bfseries (SUMMARY)}
TaBee is an Internet based application which is expected to machine translate audio recordings into instrument tablature using digital signal processing (DSP) technology and algorithm optimization. The main objective of the project is to minimize.
the labor that was necessary to translate music manually by listening to audio signals and creating playable and correct tablature on stringed instruments. The system can serve the needs of the musicians, music learners, and educators that need a practical and convenient tool of transcription by converting raw audio into musical data and optimal fret placements.

Technically, the project uses an audio analysis pipeline, which works on audio files uploaded to it to produce key musical features, including pitch, onset, and tempo. Pitches and onsets of the detected are joined together into time-aligned notes, which are assigned to the instrument fretboard according to the tuning restrictions. An optimization algorithm based on cost is used to find the most appropriate positions of the fret and strings, considering the playability and realistic fingering. This makes sure that the produced tablature is a mirror image of the musical content of the audio as well as the physical limitations of the instrument.

TaBee is a modular web application that has frontend, backend and audio processing modules. The user interface will enable the musicians to see the generated tablature where it can be played along with the original audio, tempo modified, looped.
sections and export in standard formats e.g. MIDI and JSON. The project at the current stage is aimed at developing a stable end-to-end pipeline that becomes the basis of further development like the audio source.
separation and enhanced optimization methods.

In its final form, TaBee also includes a social and organizational layer around the generated tablatures. Users can create personal profiles, follow other users, favorite generated tabs, create playlists, save public playlists, and discover tabs or playlists produced by other musicians. This makes the project more than a single-purpose transcription utility. A generated tab becomes a persistent musical object that can be liked, collected, reused in a playlist, and associated with the profile of its creator. This structure is especially useful for musicians who work together in bands, classrooms, or practice groups, since they can follow each other and organize shared musical material around generated bass tabs.

\textbf{Key Features:}
\begin{itemize}
    \item \textbf{Audio Analysis Pipeline:} Detection of pitch, onset, and tempo using DSP-based methods.
    \item \textbf{Tablature Generation:} Mapping of detected notes to fretboard positions with playability-aware optimization.
    \item \textbf{Interactive Interface:} Visualization, synchronized playback, looping, and tempo adjustment.
    \item \textbf{Export Functionality:} Support for MIDI and structured JSON output.
    \item \textbf{Modular Architecture:} Separation of frontend, backend, and audio processing components.
    \item \textbf{Social Music Workflow:} User profiles, following, tab favorites, playlists, saved playlists, search, and discovery features built around generated tablatures.
\end{itemize}

\section{Introduction}

\subsection{Motivation}
Automatic Music Transcription (AMT) is one of the major challenges of Music Information Retrieval (MIR). The standard notation (including sheet music) systems are widely used and apply to most instruments, but they do not offer the specific physical execution instructions that are necessary for stringed instruments. The frequency of a note can be achieved on the fretboard in a variety of different places, and in order to play the note properly, it has to be in a position that is as comfortable as possible to the bass guitarist, which can be a challenging optimization problem. Existing commercial software (such as Melodyne, Riffstation) tend to be based on general frequency detection and chord recognition, without taking into account the biomechanics of bass guitar playing. 

The TaBee project tries to address this by offering a complete transcription pipeline that generates optimized transcription in tablature format from raw audio. This system gives musicians more power, as it saves a time-consuming manual transcription process.

\subsection{Problem Definition}
The problem consists of two main stages:
\begin{enumerate}
    \item \textbf{Acoustic Analysis:} Extracting discrete musical notes (onset, duration, frequency) from a continuous, noisy waveform.
    \item \textbf{Playability Optimization:} Resolving the string-fret ambiguity by finding the path that minimizes hand movement cost across the 4-string bass neck.
\end{enumerate}

\subsection{Project Scope and Objectives}
The project scope includes the implementation of a full-stack web application with the following components:
\begin{itemize}
    \item \textbf{DSP Engine:} A Python-based CLI tool leveraging \texttt{Librosa} for signal processing.
    \item \textbf{Core Backend:} A Java Spring Boot application utilizing \texttt{Clean Architecture} to ensure domain separation.
    \item \textbf{Presentation Layer:} A React-based interface utilizing \texttt{AlphaTab} for high-fidelity tablature rendering.
    \item \textbf{Social Organization Layer:} User profiles, following, tab favorites, playlist creation, saved playlists, and discovery features that allow musicians to organize and share generated tablature.
\end{itemize}

\subsection{Thesis/Project Contribution}
This work adds a biomechanically-inspired cost-function-based approach to tablature generation in a deterministic manner. In contrast with the stochastic methods (e.g., the Genetic Algorithms), we use graph-based Viterbi optimization that yields a globally optimal solution with time complexity $O(N \cdot S^2)$ and is suitable for real-time web-based applications.

\section{Comparative Literature Survey}

\subsection{Automatic Music Transcription (AMT)}
Automatic Music Transcription (AMT) is a multi-dimensional problem in Music Information Retrieval (MIR). The difficulty in bass guitar transcription is not so much the detection of onsets and durations, as it is the problem of pitch ambiguity at the fundamental level: a given pitch can be played at a number of different combinations of frets and strings. Therefore, a high-quality AMT system needs to combine digital signal processing (DSP) and a physical constraint-aware optimization layer.


\subsection{Literature Analysis on Tablature Allocation}
There are three general approaches to fretboard mapping: rule-based systems, global optimization (GA) and probabilistic sequential models (HMMs).

\begin{enumerate}
    \item \textbf{Rule-Based Heuristics:} Early research was based on manually designed geometric constraints, including penalizing distance between successive notes. They work well for simpler melodies, but cannot be used to convey "phrasing" and are not very effective at complex syncopations, creating too stiff tablatures.
    
    \item \textbf{Genetic Algorithms (GA):} GA approaches, as shown in Tuohy and Potter \cite{Tuohy2005} are designed to solve the problem of fretboard allocation as an evolutionary problem over the chromosome. While they are good at solving near-optimal solutions for complex fingerings, they are stochastic models and can be very expensive to compute and are not well-suited to real-time applications or high throughput web backends.
    
    \item \textbf{Probabilistic Models (HMM/Viterbi):} Hori et al. \citet{Hori2013} proposed HMM-based methods, which saw fingering as a problem of transitioning through a state space. These models use dynamic programming (Viterbi) which can cut the search space complexity from exponential $O(S^N)$ to polynomial $O(N \cdot S^2)$, where $N$ is the number of notes and $S$ is the size of the state space.

\end{enumerate}

\subsection{Existing Commercial Solutions}
The commercial products, like Celemony Melodyne \cite{Melodyne} and Riffstation \cite{Riffstation} are the most common solutions in the market, but they are considered as "black boxes". Melodyne features a very powerful polyphonic spectral separation, but doesn't have instrument-specific fretboard information: it will only generate abstract pitch information. Riffstation offers chord extraction, but it does not take into account the single-note pluck dynamics needed to obtain bassline accuracy. TaBee is distinguished by its openness, extendability and its ability to explicitly map frequencies onto a 4 string bass neck using a deterministic, cost-aware optimisation function.

\subsection{Contribution of this Study}
This project builds on the current probabilistic models, in which the underlying algorithm is based on HMMs (which require a lot of training) instead of the Viterbi algorithm, which only has a cost-function. This separation of the DSP (Python) and optimization (domain layer) processes allows for the music to be synthesized accurately yet deliver a response time appropriate for interactive web environments, a feature not found in most academic models.

\section{Developed Approach and System Model}
\label{sec:system_model}

TaBee has been created as an end-to-end web application for creating, storing, viewing and sharing bass guitar tab from audio recordings. It can be used as a standalone transcription script, but the system includes a modern web interface, a Spring Boot REST backend, a PostgreSQL persistence layer and a digital signal processing (DSP) core written in Python. This separation enables the user-facing product characteristics and the computational audio analysis workflow to develop separately and remain unified, as one single application.


There are two key engineering challenges. First, it is required to convert the continuous audio signal into a discrete set of note events, specifying when, what, how much, and how confident they are, and the duration (just how long, or brief). Secondly, the abstract notes need to be transcribed as actual bass tablature. D2 (for example) can be played on different strings and frets depending on context. So, TaBee doesn't just detect the pitches, it adds a playability optimization stage that takes a string/fret path through the entire bass line that is coherent across the board.

\begin{figure}[H]
    \centering
    \includegraphics[width=\linewidth]{High_Level_TaBee_System_Arch.png}
    \caption{High-level architecture of the TaBee platform.}
    \label{fig:tabee_system_architecture}
\end{figure}

In a high-level view, the procedure starts with documents having uploaded an audio file from the generation page. This is done on the backend by validating the file, then creating a temp workspace for processing, running the Python command line processor, reading the generated output JSON result, persisting the tab metadata and generated note events, storing the original audio file, and returning the generated tab to the frontend. At the front end, the output is then displayed as interactive tab and offers playback-oriented controls for studying the output generated by the engine.

\subsection{System Components}

It is organized around four major components of implementation:

\begin{itemize}
    \item \textbf{Frontend Application:} A React/TypeScript app with Vite. It includes authentication screens, dashboard and discovery views, tab generation and tab viewing, playlists, profile pages and user interaction features like favorites and following.
    \item \textbf{Backend Application:} A REST API built in the Java Spring Boot framework that handles user authentication, authorization, tab ownership, playlist management, social interactions, media serving, and orchestration of the audio-to-tab processing workflow.
    \item \textbf{Python Processing Core:} Note Detection and Tab Generation Subsystem implemented in Python Modular Code. It is based on \texttt{librosa} and \texttt{numpy} for audio analysis, and it separates the reading of the audio files, pitch estimation, fretboard modeling and optimization into explicit interfaces.
    \item \textbf{Persistence and Media Storage:} PostgreSQL is used to store tab metadata, relationships, users, playlists. Separate audio files are uploaded and then referenced in the generated tab payload which will allow the tab view to display the tab and listen to the audio at the same time, enabling a visual inspection of the tab.
\end{itemize}

\subsection{Data and Persistence Model}

TaBee uses a mixed persistence model. Stable application entities are stored in relational tables, and the generated musical payload as structured JSON. This design allows for the data of the most frequently requested information to remain normalized and efficient, such as users, titles, playlists, favorite counts etc., and also provides flexibility for the generated note events, whose shape can be changed as the transcription engine gets better.

\begin{figure}[H]
    \centering
    \includegraphics[width=\linewidth]{entity_relationship_diagram.png}
    \caption{Entity-relationship overview of TaBee's persistence model.}
    \label{fig:tabee_er_diagram}
\end{figure}

\subsubsection{Core Musical Entities}

The main entity in the system is \texttt{Tab}. A tab is owned by a user, and it has a name and possibly artist metadata, with a pointer to a record (called \texttt{TabData}) that stores the generated musical data. The separation helps the application to list, search, favorite and organize tabs without loading the complete generated note structure every time.

\begin{table}[H]
    \centering
    \begin{tabular}{|p{0.24\textwidth}|p{0.62\textwidth}|}
        \hline
        \textbf{Entity} & \textbf{Responsibility} \\
        \hline
        \texttt{User} & Stores account identity, profile metadata, and ownership information. \\
        \hline
        \texttt{Tab} & Stores user-owned musical metadata such as title, artist, creation time, and update time. \\
        \hline
        \texttt{TabData} & Stores tuning, estimated tempo, and the generated JSON transcription payload. \\
        \hline
        \texttt{GeneratedTabResult} & Represents the Python processor output transferred through the backend as structured note-event data. \\
        \hline
    \end{tabular}
    \caption{Core data entities used for generated tablature.}
    \label{tab:tabee_core_entities}
\end{table}

The resulting payload contains a summary of statistics, a list of note events generated, and also instrument type, source audio reference, estimated tempo, and tuning. Time, duration, frequency, note name, MIDI number, fret, string number, note confidence can be added to each note event. This is directly useful to the frontend renderer as the client can build the musical result from a single API response.

\subsubsection{Social and Discovery Entities}

TaBee also has a dedicated group of social and organizational behavior relational entities. UserPlaylist contains user-created playlists, and FavoriteTab contains which users liked/saved a tab. The many-to-many relationship between playlists and tabs is represented by PlaylistTab, which lets multiple tabs be associated with a single playlist and multiple playlists be associated with a single tab. SavedPlaylist is a type of playlist that a user wants to store but for which he or she is not the owner, and UserFollow is a type of follow relationship between user profiles. These tables enable discovery pages, public profiles, favourite counts, saved collections and playlist-based organisation without compromising on the ownership/referential integrity of the tables. When finished with the audio processing phase, this data model is given to the generated tablature, creating a social lifecycle for it. A tab will be owned by its creator, but others can favorite it, add it to their playlists, or find it via search and public profile pages. Likewise, a playlist can be a set of rehearsal pieces, a learning collection or a common musical reference to pieces which are being performed together. The followin relationship enhances this workflow by enabling users, particularly bandmates and/or classmates, to remain updated on one another's created tabs and playlists. In this way, TaBee bridges the gap between the technical transcription and collaborative habits of musicians.

\subsubsection{Audio Storage Model}

Note data generated and raw media are kept apart. When a file is uploaded during generation, it is saved in the temp processing folder with the back-end, sent to the Python processor, and then stored with the back-end's audio storage service. This is referenced in the final tab JSON. This prevents storing large binary audio data in the PostgreSQL rows, but allows tab view to load the audio to be played.

\subsubsection{Rationale for Hybrid Relational and JSON Storage}

The selected storage model provides high query performance and flexibility in the music. Stable and lasting product concepts like ownership, playlists, and favorites work well in relational tables. However, generated tablature is most naturally stored in a nested document, since it has many musical and physical properties in each note event and future versions may add fields like articulation, quantized duration, beat position, or correction history. Having this payload stored as JSON removes the need to have unnecessary relational fragmentation and simplifies the API contract for the front-end.

\subsection{Structural Model}

The TaBee backend is structured around feature domains, not technical folders. This implies that entities, repositories, services, and user functionality are packaged under \texttt{user}, playlists under \texttt{playlist}, authentication and security under \texttt{authentication}, audio under \texttt{audio} and common infrastructure under \texttt{common infrastructure} and tab-related entities, repositories, services, and user functionality are packaged under \texttt{tab}. This organisation provides the code being easier to navigate since it separates the concerns of each feature area in the web, service, and persistence layers.

    \item \textbf{DTOs:} The API boundary is defined by "DTOs": Request and Response DTOs. They make it hard for persistence entities to be the public contract, and allow for internal model evolution.
    \item \textbf{Services:}     Application-level behavior, validation, ownership checks, and orchestration are implemented via the services, e.g., \texttt{TabService} and \texttt{TabProcessingService} and \texttt{PlaylistService} and \texttt{AuthService}.

\subsection{Object-Oriented Design and Extensibility}

The principles of object-oriented design are at the core of TaBee's implementation, given the potential for the project to expand beyond a single algorithm for transcription. New pitch estimators, alternative fretboard optimizers, new instruments, new tunings, and other storage/rendering mechanisms will be added to future versions. This current design, therefore, does not hardcode all of these decisions into one monolith, but instead distributes these responsibilities into classes, interfaces, DTOs, repositories and service boundaries.

\subsubsection{Open/Closed Principle}

The Open/Closed Principle: "A software organization should be open for extension and close for modification. This is most clearly seen in TaBee's Python transcription core, which relies on the abstraction of \texttt{Fretboard} and \texttt{TabOptimizer} and doesn't rely on a specific fretboard or a specific optimization algorithm. Therefore, a new machine learning based optimizer, rule tuning, or a new genre specific playability based optimizer may be introduced as a new implementation of \texttt{TabOptimizer} without modifying \texttt{TabGenerationService} itself.

In note detection, there is also the same extension point, \texttt{NoteDetectionPipeline} can be used with any type of \texttt{PitchEstimator} implementation. The current implementation is based on \texttt{OnsetPitchEstimator} which is based on pYIN, but a neural estimator of pitch or a different DSP method could be added in the future, under the same name. The pipeline would also coordinate the preprocessing, pluck detection, pitch estimation, tempo estimation and note construction without any knowledge of the internal workings of the estimator.

\subsubsection{Dependency Inversion Principle}

The Dependency Inversion Principle, too, is reflected in the core design. High level modules rely on the abstractions rather than low level details:

\begin{itemize}
    \item \texttt{NoteDetectionService} depends on \texttt{AudioReader}, while \texttt{LibrosaAudioReader} is only one concrete adapter.
    \item \texttt{NoteDetectionPipeline} depends on \texttt{PitchEstimator}, while \texttt{OnsetPitchEstimator} is the current concrete estimator.
    \item \texttt{TabGenerationService} depends on \texttt{Fretboard} and \texttt{TabOptimizer}, while \texttt{BassFretboard} and \texttt{PlayabilityOptimizer} provide the default bass-specific behavior.
\end{itemize}

This design isolates main orchestration logic from external libraries or algorithm details. For instance, the pipeline is not directly wrapped as a concrete audio and pitch implementation, but rather \texttt{librosa} is used within them. This makes it easier to test and allows for future replacement.

\subsubsection{Single Responsibility and Encapsulation}

The implementation is divided into small classes with narrow responsibilities, with the process of detecting pitch separated into \texttt{NoteDetectionPipeline} that coordinates the detection process, and \texttt{OnsetPitchEstimator} that contains the pitch estimation behavior. \texttt{BassFretboard} models tuning, string numbers, fret limits and generates candidates, while \texttt{PlayabilityOptimizer} evaluates local and transition costs and computes the optimal path. \texttt{TabExportService} transforms the internal results to JSON output and \texttt{TabRenderer} renders the ASCII tab.

Such separation facilitates encapsulation. The movement-cost formula is buried in \texttt{PlayabilityOptimizer}; the formula is only used to optimize a candidate sequence. The tuning and fret calculations are all in \texttt{BassFretboard} and the caller only requests a valid position. The backend, too, wraps up persistence in repositories, application behaviour in services and API contracts in the DTOs.

\subsubsection{Interface Segregation and Substitutability}

TaBee provides small interfaces, each of which has a particular specific function, instead of a single transcription interface. \texttt{AudioReader} is for loading audio, \texttt{PitchEstimator} is for estimating pitch values from pluck candidates, \texttt{Fretboard} is for returning valid physical positions, and \texttt{TabOptimizer} is for selecting an optimized path. This adheres to the Interface Segregation Principle as it makes a class only depend on the operations that it requires.

The design also is substitutive. Any class that implements \texttt{TabOptimizer} can be given to \texttt{TabGenerationService} as long as it returns a valid sequence of fret positions, by providing the fret positions of the given candidates. As long as any class that implements \texttt{PitchEstimator} returns pitch and confidence sequences which are aligned with pluck candidates, it can be used by \texttt{NoteDetectionPipeline}. This allows new implementations to be added to the existing callers with minimal risk.

\subsection{Dynamic Model: End-to-End Tab Generation Workflow}

The primary dynamic process of TaBee is to create a tab from a recorded audio file. This implementation employs process isolation between the Java Web App and the Python DSP core. The Spring Boot backend calls \texttt{cli/audio\_to\_tab.py} with a call to an external process, and waits for the result after a configured timeout. This design places all the Python audio dependencies outside of the Java runtime and provides the backend with a more clearly-defined failure boundary: when the audio processing fails, times out, or results in an invalid JSON, the backend may return a controlled error message.

\begin{landscape}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\linewidth,keepaspectratio]{workflow.png}
    \caption{End-to-end sequence of the TaBee tab generation workflow.}

The workflow proceeds as follows:

\begin{enumerate}
    \item The user chooses from an audio file on the generation screen. The frontend is now accepting the user's instrument selection and title and sends the file to the backend generation endpoint.
    \item The back-end checks to make sure the file has been uploaded, and that the extension and content type are allowed. It currently supports the input files: \texttt{.wav}, \texttt{.mp3} and \texttt{.mp4}.
    \item A temporary processing directory is set up. The file uploaded is copied to this directory, and paths are created for the JSON output file, ASCII tablature output file, and processor log file.
    \item The back-end passes the AudioPath and the JSON / ASCII output paths, along with the tuning parameter, to the Python command-line processor.
    \item The Python processor loads up the audio, performs note detection and outputs playable string/fret assignments, exports JSON with the option to export an ASCII preview of the tab.
    \item The backend deserializes the generated JSON into a typed \texttt{GeneratedTabResult} record, and uses the tab service to generate a persisted tab.
    \item The original audio file is kept and added to the tab JSON payload.
    \item The result is added to the generated tab view, and the frontend goes there for navigation, rendering, playing, favoriting and organizing this result.
\end{enumerate}

\subsection{Signal Processing Pipeline}

The Python note detection pipeline converts a raw wave to a series of note events. It is realized by the classes \texttt{NoteDetectionPipeline} that is implemented by the class \texttt{BassPluckDetector} and by the class \texttt{OnsetPitchEstimator}. The pipeline is deliberately independent from tab generation, allowing it to determine whether what has been played has been heard, and the latter stage of tab generation to determine the location of those notes on the bass fretboard.

\begin{algorithm}[H]
    \caption{Bass Note Detection Pipeline}
    \label{alg:tabee_note_detection}
    \begin{algorithmic}[1]
        \State \textbf{Input:} Audio waveform $y$, sample rate $sr$
        \State Trim leading and trailing silence from $y$
        \State Normalize $y$ by its maximum absolute amplitude
        \State Detect bass pluck candidates from the preprocessed signal
        \State Estimate $f_0$ values for each candidate using pYIN within the bass frequency range
        \State Stabilize detected frequencies against octave and harmonic errors
        \State Estimate tempo from median inter-onset interval
        \State Build detected note events with time, frequency, and confidence
        \State \Return Detection result
    \end{algorithmic}
\end{algorithm}

In the preprocessing stage, silence is removed from the speech signal by applying an amplitude threshold and the signal is then normalized. This minimizes the impact of the volume difference to be captured and the effects of the onset and pitch stages on the captured input range.

The onset stage is dedicated to bass plucks. Instead of each of these small spectral fluctuations being a single note, the detector identifies candidate pluck positions which are likely note attacks. These are the time points in a track that are used to anchor pitch estimation.

Pitch estimation is done not at the attack transient, but after each pluck candidate. This is useful because the initial assault on a bass note will contain noise, string contact artifacts, and unstable harmonics. The \texttt{OnsetPitchEstimator} is therefore used to read pitch from a short window following the onset. The frequency range is set to 32 Hz to 220 Hz, which is the typical low register range of bass guitar notes, with the use of librosa.pyin. The resulting frequencies are then clustered and stabilized by the estimator, to minimize octave errors and harmonics misreadings.

Tempo is estimated by measuring the interval between the onsets detected. It calculates inter-onset intervals, takes a median interval value as a strong central value and bends the resulting tempo into a favorite musical range. This stage outputs a \texttt{DetectionResult} object that includes onset time, pitch, note, tempo estimate, and detection of pluck candidates.

\subsection{Fretboard and Playability Optimization}
Pitch detection is not sufficient to create high quality tablature since tablature is a physical manifestation of music. On a bass guitar, there can be more than one string/fret combination to play the same pitch. TaBee implements a fretboard model and a dynamic programming optimizer to clear up this ambiguity.

The \texttt{BassFretboard} model can be used for standard 4 string bass tuning \texttt{EADG}, 5 string bass tuning \texttt{BEADG}, dropped-C tuning \texttt{CGCF}, and half-step-down tuning \texttt{EBABDBGB}. Numbers are written from treble to bass strings on a string. The string and fret numbers are based on the selected tuning; for standard bass, 1 is G2, 2 is D2, 3 is A1, and 4 is E1. For every note picked up by the MIDI controller, the fretboard model calculates all possible positions that can be played on the fretboard up to the set maximum fret.

\begin{table}[H]
    \centering
    \begin{tabular}{|p{0.2\textwidth}|p{0.2\textwidth}|p{0.42\textwidth}|}
        \hline
        \textbf{Stage} & \textbf{Input} & \textbf{Output} \\
        \hline
        Pitch conversion & Frequency in Hz & MIDI note and note name \\
        \hline
        Bass normalization & MIDI note & Bass-register MIDI note after octave correction \\
        \hline
        Candidate generation & MIDI note and tuning & Valid string/fret positions \\
        \hline
        Playability optimization & Candidate sequence & Globally optimized string/fret path \\
        \hline
    \end{tabular}
    \caption{Transformation from detected pitch to playable bass tablature.}
    \label{tab:tabee_pitch_to_tab}
\end{table}

It is implemented by \texttt{PlayabilityOptimizer}. It is based on a dynamic programming technique similar to the Viterbi algorithm. The state of each candidate is considered as a possible state for a note, and the movement cost between two consecutive notes is assigned for each possible move. The algorithm calculates the path cost for all the states visited and backtracks through the path to find the path with the lowest cost and recover the cost preferred path globally.

\begin{algorithm}[H]
    \caption{Playability-Based Fretboard Optimization}
    \label{alg:tabee_playability_optimizer}
    \begin{algorithmic}[1]
        \State \textbf{Input:} Candidate positions $C_1, C_2, ..., C_N$
        \ForAll{candidate $c$ in $C_1$}
            \State $dp[1][c] \gets localCost(c)$
        \EndFor
        \For{$i = 2$ to $N$}
            \ForAll{candidate $c$ in $C_i$}
                \State $dp[i][c] \gets \min_{p \in C_{i-1}} dp[i-1][p] + transitionCost(p,c) + localCost(c)$
                \State Store best predecessor $p$ for backtracking
            \EndFor
        \EndFor
        \State Backtrack from the lowest-cost candidate in $C_N$
        \State \Return Optimal string/fret path
    \end{algorithmic}
\end{algorithm}

Local cost function represents preferences for single positions. It features a moderate-high-fret penalty, open-string playing and a desire to use low position fingerings where they are convenient. The transition cost function is an estimation of the movement costs between two successive notes, based on fret distance, string distance and hand position change. Open strings and rests are treated specially as they can shorten or reset the LHS movement. This helps TaBee to not only move to the lowest fret each time, but also avoids picking locally convenient frets that would make awkward jumps later in the piece.

The model of fretboard will return a rest if a note cannot be mapped to a playable position under the selected tuning. This way, the optimizer and exporter can proceed with the rest of the sequence without stopping because one specific detection was not playable, but instead fail the entire file.

This concept is shown in figure \ref{fig:tabee_fretboard_optimization} using a simplified 3-note phrase. Detected Pitches A2, B2 and C3 can be played on many positions on a standard bass fretboard. For instance, A2 may be used on fret 2, string G; fret 7, string D; or fret 12, string A. If the system were to pick every note up individually, then it would be able to pick a note that might be technically correct but awkward for the next transition. On the contrary, the optimizer analyzes the entire selection of the potential positions and picks the bolded sequence of positions. In this example, playing a G string throughout the 2nd, 4th and 5th frets is a low-cost movement path to play, rather than any options that would involve a higher fret jump or unnecessary string changes.

\subsection{Software Design Patterns and Principles}

Several software design principles are used to ensure maintainability, testability and future extensibility.

\begin{itemize}
    \item \textbf{Feature-Based Modularization:} There is no one single hierarchy in the backend code but multiple hierarchies based on the functionality on each feature — tabs, users, playlists, authentication, and media.
    \item \textbf{Repository Pattern:} Spring Data JPA repositories provide abstraction to access a database and separate persistence information from web controllers.
    \item \textbf{Service Layer Pattern:} The services implement application behaviour like creating tabs, updating tab validation, ownership checking, playlist operations, audio processing orchestration, etc. - this is known as Service Layer Pattern.
    \item \textbf{DTO Boundary Pattern:} Using DTOs for Request and Response to create stable API contracts and to avoid direct persistence entities reaching clients.
    \item \textbf{Ports and Adapters in the Python Core:} Interfaces like \texttt{AudioReader}, \texttt{PitchEstimator}, \texttt{Fretboard} and \texttt{TabOptimizer} separate the orchestration of the pipeline from the concrete DSP and optimization implementations.
    \item \textbf{Strategy-Like Optimization Abstraction:} The playability optimizer is replaceable in the \texttt{TabOptimizer} port, which is referred to as Strategy-Like Optimization Abstraction. New algorithms, like instrument specific heuristics or learned fingering models, could be added into the same interface.
    \item \textbf{Process Isolation:} The Java backend calls the Python processor as an external process, as a timeout and log capture. This separates, from the rest of the web runtime, the heavy audio dependencies and sets them up as a definite failure boundary.
    \item \textbf{Security and Ownership Checks:} The operations of tabs/playlists are directed to services that impose ownership and visibility constraints, and authenticated endpoints require the current user.
    \item \textbf{Testability:} Separating the controllers, services, repositories, DTOs, and Python ports enables unit tests to focus on individual behaviors rather than the whole stack.
\end{itemize}

\section{Experimentation Environment and Experiment Design}
\label{sec:experiments}

There are two evaluation targets at the TaBee project. The first objective is to get the music correct along the audio-to-tab pipeline: the system should be able to identify bass note events and correlate them with playable string/fret locations. \subsection{Experiment Design}

The algorithmic experiment is executed in three stages of the algorithm, to enable errors to be isolated to the appropriate step in the pipeline.

\subsubsection{Onset and Pitch Detection Experiment}

The focus of the first experiment is to determine if the system is able to recognize the proper note events from the sound. The onset time detected is compared to the annotated onset time with a temporal tolerance window. A detected onset within the tolerance window of an unmatched ground truth onset is considered correct. Then it is determined if the pitch of the detected MIDI note is correct for the matched onset, by comparing the detected note with the annotated note.

The key performance indicators are precision, recall, and $F_1$ score:

\begin{equation}
Precision = \frac{TP}{TP + FP}
\end{equation}

\begin{equation}
Recall = \frac{TP}{TP + FN}
\end{equation}

\begin{equation}
F_1 = 2 \cdot \frac{Precision \cdot Recall}{Precision + Recall}
\end{equation}

These event-based measures should also be supplemented by a tracking of octave errors. A common problem with bass transcription is that low frequency fundamentals could be weaker than their harmonics, thus leading to mistakes in octave. A separate Octave-error count allows separation of timing errors from frequency estimation errors.

\subsubsection{Fretboard Assignment Experiment}

In the second experiment, the output of the playability optimizer is being tested. Each time a pitch is correctly detected the system creates candidate string/fret positions, and chooses an optimized string/fret path. The output can be assessed with the following:

\begin{itemize}
    \item \textbf{Exact Assignment Accuracy:} Percentage of notes for which the resulting string and fret are the same fret as the reference string.
    \item \textbf{Equivalent Assignment Accuracy:} Percentage of notes that are musically equivalent (and accepted by the annotation set) to the generated position.
    \item \textbf{Average Movement Cost:} Cost of optimizer divided by number of transitions, to compare alternative optimizer settings.
    \item \textbf{Unplayable Note Rate:} Percentage of notes that do not have a valid position when using the current tuning.
\end{itemize}

\subsubsection{End-to-End Processing Experiment}

In the third experiment, the entire upload-to-render process is tested. This experiment is the same but it uses an audio file that is submitted to the frontend or backend endpoint, which is processed by the Python core, stored by the backend and rendered by the frontend. This test ensures that valid audio doesn't just work in the Python script but also in the actual product workflow.

\subsection{Threats to Validity}

The interpretation of the evaluation needs to take into account several limitations:

\begin{itemize}
    \item The existing assessment programme is based on a small number of monophonic bass recordings. More data and more diversity would be required for making definite generalization statements.
    \item There may be more than one string/fret assignment that is musically correct for the same pitch sequence. Therefore, in addition to the exact matches, there should be also equivalent accepted fingerings.
    \item The existing pipeline mostly supports mono bass input.The existing pipeline is geared mostly towards mono bass input. Recordings of full-band mixes or chordal/polyphonic music are not the primary use case and should not be seen as such.
    \item Local Performance Scope: Now the performance measurements are local micro benchmarks. They prove selected operations are light weight, but do not stand in for production-scale concurrent load testing.
    \item Database and mail configuration will affect full integration behaviour - External Service Availability. Automated tests explicitly do not need to use external services, which ensures that the local regression tests will not change.
\end{itemize}

The half-step-down rock/punk subject preserved most repeated-note events but included a small number of extra or shifted detections, which reduced the scored excerpt accuracy.

Before final numeric evaluation, it is obvious that the design has an edge over the purely greedy mapper. A greedy mapper can select the lowest fret or nearest fret for each note, without taking into account the repercussions on subsequent moves. TaBee maintains cumulative path costs and backpointers, therefore the chosen fingering is optimized throughout the whole sequence detected. The complexity is $O(N \cdot S^2)$, where $N$ is the number of notes, and $S$ is the number of candidates per note. This is an OK cost for an interactive file-based process, as a bass note typically has only a few possible string/fret combinations.

The drawback is that the current optimizer is a heuristic as opposed to a learned one based on human performance data. Its local and transition costs reflect reasonable playability assumptions including a cost of making a large fret jump and a cost of skipping a string, but fingering the correct notes may vary by style. A player can choose to play a higher pitch for tone, timbre, muting or preparing for a subsequent phrase. It is worth noting, however, that the notion of equivalence in playable assignments is not as straightforward as exact equality and could be a more accurate measure than exact equality.

\subsection{Discussion of Limitations}

There are also some weaknesses identified in the evaluation. For now, the line is geared towards mono bass recordings. Onset and pitch accuracy might be affected by full-band mixes, chords, slap artifacts, distortion or noisy environment. Second, current optimizer has deterministic playability heuristics. These are explainable and efficient but not all of the stylistic choices of fingering. Third, the current automated test suite is relatively focused on backend validation, dto mapping, security related file handling and performance microbenchmarks. The quantitative audio evaluation demonstrates the pipeline on the first seven manually checked subject groups in the evaluation dataset, but a larger annotated dataset and repeatable browser-level system tests would be needed for stronger generalization claims.

In spite of the above restrictions, the system shows it is possible to go from audio in to tab out. The architecture is modular and allows for future improvements: the pitch estimator, fretboard model and optimizer can be replaced with new modules, and the frontend and backend already contain the product infrastructure necessary to expose new transcription results to users.

\section{Conclusion and Future Work}
\label{sec:conclusion}

The aim of this project was to create an end-to-end web-based application that generates bass guitar tabs from uploaded audio files. The project started with a real musical challenge: manual transcription is both time-consuming and many existing tools only stop at pitch detection or offer closed and non-customisable workflows. TaBee's aims to fill this void with a bass oriented audio analysis pipeline, string/fret playability optimizer, and full stack audio tab storage, rendering, playing, organising and sharing application.

The finished system is proof that automatic transcription is not just a signal processing problem, but one that can be viewed as a software engineering problem. The Python core is used to detect bass note events using onset candidates and pYIN-based pitch estimation and to transform the detected pitches into playable tablature using a fretboard model and Viterbi-style dynamic programming optimizer. The Java Spring Boot backend performs validation on the uploaded file, initiates the processor under a controlled process boundary, saves the generated tabs in the database, saves references to the audio content and provides REST APIs for the user-facing components. The React frontend utilizes AlphaTab to generate results and enable product features like tab viewing and playback, playlists, favorites, discovery, profiles, and search.

From the architectural point of view, the most important feature of TaBee is its domain-specific transcription core and the usable web platform. As the audio processor, backend services, persistence model and frontend renderer are separate modules, they can be tested and improved independently of each other. The automated test suite as it is currently configured passes 29 tests as shown in the back end test report, including tests for password validation, media validation, audio upload validation, token behavior, DTO mapping and selected performance metrics. The results confirm the reliability of the application layer, while the short-phrase audio evaluation provides a measured validation of the transcription path under the selected dropped-C tuning.

The project also demonstrates the significance of modeling specific to bass. As with tablature, if there is a detected pitch, it is not enough to write full tablature because if it is the same pitch could be at two fretboard positions. To remove this ambiguity, TaBee's playability optimizing algorithm chooses a consistent string/fret path through the detected note sequence. This makes the output from the code more useful to bass players than a list of note names or frequencies.

\subsection{Future Work}
TaBee has the essential features of the audio-to-tab process and the overall product line, but a few enhancements would make the entire system more accurate, scalable, and appreciated by musicians.

\begin{itemize}
    \item The next step is to expand the manually annotated dataset beyond the current evaluated subject groups. Additional isolated-note samples, standard-tuning phrases, alternate-tuning phrases, and longer bass-only song excerpts from different genres would make the algorithmic evaluation more stringent and allow future versions of the pipeline to be evaluated objectively.
    \item Note timing and tempo estimation is current, but rhythm notation can be further improved. What remains to be done is beat-grid alignment, bar-aware grouping, rests, more accurate duration quantization, etc. to render.
    \item \textbf{User Correction Workflow:} Automatic transcription is not always accurate. One of the more useful features would be the ability to edit an erroneous note, alter string/fret positions, fine-tune timing, and restore saved versions. These corrections may be used for training and/or evaluation data at a later time.
    \item The current system is mainly monophonic bass oriented. Future versions can incorporate source separation, bass stem extraction and polyphonic transcription methods, allowing users to upload full-band recordings rather than bass tracks only.
    \item Expanded Instrument and Tuning Support: The fretboard abstraction can be extended to 6 string guitar, UKE, alternate bass tunings and extended range basses. That would be a tuning definition, string ranges and playability heuristics per instrument.
    \item The current optimizer employs a set of hand-movement heuristics which are deterministic. One future system might be able to learn the preferred fingerings from transcriptions by the pros, or it could adjust the costs depending on the tastes, styles and/or preferences of the user.
    \item The background job processing is currently handled by the background process running a controlled external python processor. If used by multiple users and/or large files, the system could be transformed to a background job queue, reporting progress, provide means to cancel a job, handle re-challenges, and persist job states.
    \item End-to-end automated tests using a browser testing tool would add to the confidence of each step of the workflow from the registration and upload to the rendered tab playback and playlist organization.
    \item Future work should implement a performance and scalability evaluation for processing time and upload concurrency, as well as for the latency of the queries to the audio database and for the latency of the rendering of long tabs on the frontend.
\end{itemize}

To wrap up, TaBee provides a starting point for automated generation of bass tablature. At present, it is being used to integrate into a single system the following components: DSP, playability optimization, web architecture, persistence, and user-facing workflows. The increase in the number of annotated evaluation set, editing tools and more advanced audio processing makes it possible for TaBee to grow from a prototype graduation project to actually become an assistant for musicians who want to learn, preserve, and easily share bass lines.
